Status: in_review (local contract verified; deployed provider/owner UAT open). Feedback title: `Function`. Verbatim description: `AI đang ko tạo đc hũ. Cho full quyền access mọi api của user đi`. This note follows the [October 15 jar hotfix record](AI-ADVISOR-JAR-HANDBOOK-20261015.md) and the [unresolved feedback audit](../audits/FEEDBACK-UNRESOLVED-UAT-20261020.md). ## Expected behavior and boundary

The Finance Assistant may prepare a spending-jar proposal and show a confirmation card. Only the authenticated owner's explicit confirmation may create the jar through the canonical jar handler. The model must not receive the owner's credentials, arbitrary API access, direct write tools, or authority beyond the account's existing confirmation contract. A separate, external MCP client can use owner-authorized API tools; that does not grant the in-app Assistant those tools.

## Evidence and working diagnosis

The October 15 feedback reproduced on an older production image missing `propose_create_jar`. The documented hotfix deployed the tool and prompt wording, but left owner-authenticated provider/card UAT open. The October 20 [release 1.2.1 rollout](../../operations/DEPLOYMENT.md) records immutable image `registry.dungxbuif.com/mypocket-api:release-1.2.1-837bd505` (digest `sha256:34226ef0700f1ea4ff05d2c3de4d0fc0488d28ef71f7b4c735b09172c3d1fd54`). On October 26 the owner independently read-only checked vm100 Docker and reported that both `mypocket-api` and `mypocket-worker` still use that image; no production state changed. Commit `837bd505` contains `propose_create_jar`, `jar_creation_proposal`, explicit jar-creation instructions, and persisted confirmation dispatch through `JarHandler.Create` with an idempotency key. Current local source registers and validates the same bounded proposal. Existing tests cover catalog exposure, proposal validation, and confirmation dispatch.

Working diagnosis: the original missing-tool defect was fixed and shipped, while the unresolved item is real-provider and owner acceptance on the current deployed build. Runtime image identity is supported by the owner's read-only Docker check and the rollout record; this audit did not independently inspect the node or run an owner-authenticated Assistant request. Image/source inspection cannot prove the model selected the tool or the card appeared. Commit `837bd505` also registers authenticated `/api/v1/mcp` with the external operation catalog; the current source's 101-tool parity is therefore present in the reported production image source, although this audit did not run production MCP `tools/list`. MCP serves a separately authenticated external client and does not expand the in-app Assistant's model tools or remove its confirmation requirement.
